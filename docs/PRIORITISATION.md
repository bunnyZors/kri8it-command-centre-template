# Learning priorities without copying someone else's context

The template starts with no client ranks, financial assumptions or personal commitments. Pins and explicit task-level corrections lead; imminent deadlines, security/access risk, client risk and revenue-blocking work follow. Confirmed client rules break otherwise comparable ties, not override every urgent issue.

The board stores recent priority corrections with an optional reason. This is evidence reuse, not model training. One task correction is not a standing client ranking. Ask at most one narrow question when a real ambiguous choice materially changes the next three priorities. Avoid repeated broad questionnaires. Record standing rules only with user confirmation, scope, provenance, date and confidence; distinguish fact from hypothesis and never infer revenue from message volume or brand size.

Keep human-authoritative context in the recipient's private project notes. Publish only the minimum approved policy projection in their `config/planning-policy.json` so hosted runs can read it; cloud jobs cannot edit the local filesystem. Do not send their context back to the central template. User data remains private even when the source repository is shared with staff.
