# Agent instructions — recipient-owned command centre

1. Read README.md, docs/CODEX_SETUP.md, SECURITY.md, CONNECTORS.md, SCHEDULING.md and TESTING.md under docs/ before setup. Read the current installed Sites skill and relevant references; do not invent tool names or hardcode a previous developer's plugin paths/version.
2. This repository is a template, NOT an existing personal installation. Ask timezone, working hours, account/source identity, desired cadence/times/weekends and first-scan window. Manual-only is valid. Never silently copy example preferences as confirmed answers.
3. Work in the recipient's private copy. If .openai/hosting.json already has a project_id, inspect ownership and installation records before anything else; reuse only an explicitly intended recipient-owned installation. Never publish to an unknown Site or create duplicates after an uncertain operation.
4. One person, one owner-private Site and database. No multi-user/public deployments. Hosting access is part of the security boundary; stop on any sharing mismatch. No copying runtime data, credentials, source bodies, tokens or original history into Git.
5. Prefer integrations/MCP/APIs. Computer use only for unsupported controls. Accounts require the user's own connection/consent. An interactive connector success does not prove unattended reachability.
6. Use the validation/configuration script and current Sites workflow. Preserve Kri8it branding, migrations, IDs returned by tools and the functional contracts. Store non-secret recipient setup evidence in ignored .setup/installation.json, with state pending until each gate passes. Never store credentials there.
7. Ask when/how often the briefing should run. Create/update ONE Site-linked cloud task only after consent, duplicate checking and a successful controlled run. Verify actual timing/timezone/enabled state and hosted persisted readback. A preference badge is not proof a scheduler exists.
8. Routine runs obey the published planning.playbook fetched fresh: sources read-only, bounded scans, independent failure/cursors, cross-source deduplication, preserve user edits/completed/dismissed choices, uncertainty in Review. No calendar booking, email modification or execution of tasks.
9. Be model/token efficient: metadata-first deterministic fetching, compact output, reuse unchanged recordings and light reliable effort; escalate only bounded consequential ambiguity where actually supported. Do not claim model routing or cost savings without verification. No agents merely for fetching.
10. Before handoff run relevant tests/builds, inspect the staged diff, verify owner-private deployment/anonymous rejection and source freshness. Report limitations honestly; do not claim colleague pilot complete without a second account. Do not enable new schedules or deploy while doing template maintenance.
